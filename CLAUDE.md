# Luce — напутствие для продолжающего Claude Code

Проект передан от другого агента (сессия в облаке) локальному Claude Code.
Ниже — что нужно знать, чтобы продолжить без переоткрытия уже закрытых
вопросов.

## Что это

Интерактивная веб-реконструкция световой партии («Luce») из «Прометея»
Скрябина, ор. 60, поверх настоящей музейной фотографии 12 цветных ламп
(строка "тентелевского" светового органа). Один HTML-файл, без сборки,
без рантайм-зависимостей (кроме `@import` шрифтов Google — единственный
сетевой запрос; всё остальное, включая фото и теперь шрифт «Брокгауз и
Ефрон», встроено как base64).

## Два файла — какой редактировать

- **`luce.html`** — канонический исходник. Редактируй **только его**.
  Ссылается на `luce-photo.jpg` внешним `<img src="luce-photo.jpg">`.
- **`luce-standalone.html`** — генерируется из `luce.html` (фото
  встраивается как base64). Это то, что реально скачивает пользователь —
  явное требование: «сам скрябинизатор — одним файлом делай». **Не
  редактируй его руками** — после любых правок в `luce.html` пересобери:

  ```python
  import base64
  html = open('luce.html', encoding='utf-8').read()
  photo_b64 = base64.b64encode(open('luce-photo.jpg','rb').read()).decode('ascii')
  old = 'src="luce-photo.jpg"'
  assert html.count(old) == 1
  html = html.replace(old, f'src="data:image/jpeg;base64,{photo_b64}"')
  open('luce-standalone.html', 'w', encoding='utf-8').write(html)
  ```

  Затем отдавай пользователю **`luce-standalone.html`** — по умолчанию
  ожидается доставка одним файлом, каждый раз.

## Архитектура: два независимых режима, одна UI-оболочка

1. **«Прометея»** (`render()`, luce.html:1393) — жёстко заданная по
   партитуре реконструкция, тактовая точность, источник — массивы
   `stages` (luce.html:553) и `flashes` (luce.html:565), взятые из
   музыковедческих источников. Не меняются алгоритмом — это авторские
   данные, а не результат анализа.
2. **«Другая музыка»** (`renderAnalysisFrame()`, luce.html:914) — живой
   анализ произвольного аудио через цветовой круг Скрябина. Явно
   промаркирован как *не* историческая реконструкция, а лучшее
   приближение для случайного трека.

Оба вызываются только через **`renderCurrent(elapsed)`** (luce.html:1448) —
диспетчер по `analysisMode`. Это важно: раньше `resetBtn` и обработчик
клика по таймлайну звали `render()` (режим «Прометея») напрямую в обход
диспетчера, и при перемотке в «Другой музыке» показывались ярлыки вроде
`"Fis (возврат)"`. Если добавляешь новую точку, откуда меняется позиция
воспроизведения — **зови `renderCurrent`, а не `render`/`renderAnalysisFrame`
напрямую**.

## Ключевая архитектурная идея: activeColorMap — единственный источник истины

Для «Другой музыки» когда-то было два независимых анализа: офлайн-карта
всего трека (для таймлайна) и отдельный живой Гёрцель-анализ в реальном
времени (для фона/лампы). Они регулярно расходились — пользователь много
раз присылал скриншоты «фон и лампа не совпадают с полосой». Причина была
структурной: два разных прохода почти неизбежно дают разные ответы, сколько
их ни калибруй.

**Решение**: офлайн-карта (`buildColorMap()`, luce.html:761) считается один
раз сразу после загрузки файла и кладётся в `activeColorMap` /
`activeColorMapDuration`. И таймлайн (`paintTimelineFromColorMap()`,
luce.html:1375), и фон/лампа (`renderAnalysisFrame()` через
`colorMapSegmentAt()`, luce.html:657) читают **один и тот же** массив.
Разойтись они физически не могут. Живой анализ (`getFloatTimeDomainData` +
Гёрцель по сырому сигналу) используется **только** для того, чтобы решить
*когда* мигнуть дополнительной лампой (см. блок onset-детектора в конце
`renderAnalysisFrame`) — никогда для выбора «какого цвета» фон.

**Если в будущем задача снова окажется «фон/лампа не совпадают с
чем-то» — сначала проверь, не завёлся ли где-то второй независимый
источник цвета в обход `activeColorMap`.** Это самый частый класс багов
в этом проекте.

## Метод анализа: Гёрцель, не FFT-бины

И офлайн-карта, и (опосредованно) живой дисплей используют **алгоритм
Гёрцеля** (`goertzelMag()`, luce.html:742) по фиксированному набору целевых
частот `CHROMA_TARGET_FREQS` (luce.html:734, 4 октавы C2–B5, MIDI 36–83),
а не `AnalyserNode.getByteFrequencyData()`. Раньше живой путь был на
FFT-бинах, офлайн — на Гёрцеле; несмотря на «похожие» диапазоны частот, это
принципиально разные анализы и давали разные ответы на одном и том же
звуке. Если понадобится трогать частотный анализ — держи оба пути (если
они вообще снова станут два) на одном методе, либо (лучше) сохраняй текущую
схему с единственным источником истины.

`buildColorMap()` (luce.html:761): децимация к фиксированной **частоте**
~2600 Гц (не к фиксированному числу сэмплов — на длинных файлах это раньше
роняло Найквист ниже целевых частот), `segCount = clamp(40..180,
round(duration/3))`, топ-2 ноты на сегмент (порог `rel>=0.35`), затем
`mergeIntoStructuralRuns()` (luce.html:812) — мажоритарное сглаживание ±2 и
слияние коротких пробежек (`< max(2, round(n*0.04))`) с соседями.

## Максимум ламп и «динамика» — намеренно без пользовательских настроек

Максимум одновременных ламп = **2** (константа, без слайдера) — это
единственный документированный в партитуре дубль, «без выбора». Порог
чувствительности вспышек (`dynMultiplier = 3.0`, luce.html:1038) — тоже
константа, не слайдер. Пользователь явно попросил убрать оба UI-элемента
управления этим: строгая реконструкция по умолчанию не должна давать
пользователю «подкрутить» то, чего в оригинале не было. **Не возвращай эти
слайдеры**, если только пользователь прямо не попросит другого.

## Экран не гаснет (Android) — тройная защита, статус диагностики

Три независимых, дублирующих друг друга механизма (Android оказался
ненадёжен с одним Wake Lock):
1. **Screen Wake Lock API** — `requestWakeLock()`/`releaseWakeLock()`
   (luce.html:1259, :1271). Пишет строку состояния в `wakeLockState` на
   каждую попытку.
2. **Скрытое зацикленное `<video>`** (`#nosleepVideo`) — теперь
   полноэкранное, но спрятано за `.stage` (`z-index:-1`). **Важно**: этот
   `<video>` — прямой сосед `.stage`/`.vignette`, **не внутри `.wrap`**.
   `.wrap` имеет `position:relative;z-index:2`, создаёт свой stacking
   context и раньше «ловил» отрицательный z-index видео внутри себя, из-за
   чего видео рисовалось *поверх* `.stage`, а не позади — если увидишь
   «фон сломан» после манипуляций с версткой — проверь именно это первым
   делом.
3. **Media Session API** (`if('mediaSession' in navigator)`, luce.html:1234)
   — добавлен по прямому запросу пользователя («ютуб же не гаснет!»),
   регистрирует `play`/`pause` action handlers.

Живой статус всех трёх — в модалке `#modalBackdrop` (кнопка `?`),
`#wakeLockStatus`, заполняется при открытии модалки. **Не удалён и не
протестирован до конца** — см. «Открытые вопросы» ниже.

## Проверено эмпирически (не только «выглядит нормально»)

Методология, которую настойчиво требовал пользователь: генерировать
синтетическое «эталонное» аудио прямо из `stages`/`flashes`, прогонять
через реальное приложение (Playwright), сверять количественно с известным
правильным ответом — а не полагаться на визуальную проверку. Важный урок
по пути: первый эталон был сжат до 120 секунд вместо реальных ~22 минут и
дал обманчиво хорошую метрику (96.7% точности по кадрам) при **скрытом
мерцании** (37 смен ноты вместо 6 настоящих) — на реалистичной длительности
это вскрылось. **Если пишешь новый тест синтетическим эталоном — строй его
на реальной длительности трека, не сокращай для скорости**, либо явно
проверяй количество смен состояния, а не только процент правильных кадров.

Тестовые скрипты были в scratchpad конкретной сессии и **не сохранены в
репозитории** (это были одноразовые/итеративные debug-скрипты, не чистый
код продукта) — при необходимости пересоздать методологию с нуля, это
быстро (генератор WAV из `stages`/`flashes` через `soundfile`, прогон через
Playwright). **Важно про генерацию тестовых WAV**: Python-модуль `wave`
даёт файлы, которые `<audio>` проигрывает, но `AudioContext.decodeAudioData`
отклоняет (`EncodingError`) из-за нестрогого заголовка — используй
`soundfile`/libsndfile, он даёт спек-совместимые заголовки.

Финальная проверка перед хэндоффом: реальная запись Симфонии №1 ми мажор
Скрябина (загруженная пользователем) дала цветовую карту с доминантой «E»
(верно — тональность ми мажор) и правдоподобными отходами к D/H. Перемотка
на 6 разных позиций трека дала **согласованные** `stageName`/фон/лампу на
каждой позиции (тест на реальном файле, не синтетике).

## Открытые вопросы / не проверено до конца

- ~~Настоящая запись «Прометея» не тестировалась~~ — **протестирована**
  (локально, файл 52 МБ/21:42, положен прямо в папку проекта — через чат
  не проходил по размеру). Результаты:
  - **Режим «Прометей»**: `analyzeAudioFile` корректно обрезал тишину/
    аплодисменты (муз. 0:01–21:36 из 21:42), перемотка по всей длине
    (0, 1.3, 200, 650, 1000, 1296, 1298, 1302 сек) дала монотонную
    прогрессию тактов 1→606 и стадий I→VII, на 1298+ сек — корректный
    переход в «аплодисменты». Ошибок в консоли нет.
  - **Режим «Другая музыка»**: `buildColorMap` на той же записи дал
    180 сегментов, доминанты E (110) / Fis (50) / C (20). Финал совпал с
    партитурой (последние сегменты — Fis, как и авторский «возврат»), но
    **самое начало трека анализ определил как C, а не Fis/Ges**, как в
    партитуре. Это не баг: мистический аккорд в начале «Прометея» реально
    построен от C в басу — Гёрцель честно ловит акустически сильнейший
    тон, а не синестетическую ноту Люче, которая для этого же момента у
    Скрябина — Fis. См. следующий пункт.

- **Идея на будущее (озвучена пользователем, не реализована)**: сблизить
  логику `buildColorMap`/Гёрцеля с логикой самого Скрябина — сейчас
  анализатор ищет акустически самый громкий тон, а Люче у Скрябина это
  скорее синестетическая проекция гармонического КОРНЯ (в терминах
  транспозиций мистического аккорда), не обязательно самый громкий бас.
  Варианты, не выбран ни один:
  1. Детектировать транспозицию мистического аккорда целиком (6 нот) и
     брать её корень — точнее музыковедчески, сложнее реализовать и
     протестировать.
  2. Взвешивать по кругу Скрябина (его собственное соответствие
     тон↔цвет), а не по чистой громкости — проще, но добавляет ещё один
     independent источник цвета, что CLAUDE.md выше прямо называет
     самым частым классом багов проекта (см. «activeColorMap — единственный
     источник истины»). Если делать — только ЗАМЕНОЙ текущей логики
     выбора доминанты внутри `buildColorMap`, не вторым парал­лельным
     путём.
  3. Оставить как есть: текущее поведение — честный «независимый»
     анализ, разметка ожидаемо не идентична партитуре, это уже
     задокументировано как by design.
  Нужно решение пользователя, какой путь (или их комбинация) — не
  реализовано, только исследовано и описано здесь.
- **Надёжность Wake Lock на Android вне WebView Total Commander не
  переподтверждена** после добавления Media Session и увеличения видео на
  весь экран. Ранее диагностировано: `NotAllowedError` при попытке Wake
  Lock, и страница открывалась внутри **встроенного файлового просмотрщика
  Total Commander** (`com.ghisler.files` в адресной строке) — это
  урезанный WebView, который может отказывать в разрешении на Wake Lock
  в принципе. Пользователю посоветовано открыть файл в обычном браузере,
  но живого подтверждения «в обычном Chrome на Android экран не гаснет»
  после всех трёх исправлений пока не было.
- Шрифт «Брокгауз и Эфрон» встроен и подтверждён рендерящимся
  (`document.fonts.check(...)` === true, визуальный скриншот сделан), но
  не проверен на реальном Android-устройстве пользователя, только headless
  Chromium.

## Данные партитуры — не трогать без источника

`stages` (luce.html:553), `flashes` (luce.html:565) и `lampSpotsData`
(luce.html:586, координаты ламп — измерены по пикселям реального фото
через weighted-centroid, не геометрическая догадка) — авторские/измеренные
данные, не результат алгоритма. Если пользователь просит «поправить»
что-то в самой партитуре «Прометея» — это правка данных по источнику, а не
тюнинг анализа.
