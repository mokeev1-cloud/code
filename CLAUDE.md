# Luce — напутствие для продолжающего Claude Code

Проект передан от другого агента (сессия в облаке) локальному Claude Code.
Ниже — что нужно знать, чтобы продолжить без переоткрытия уже закрытых
вопросов.

## Что это

Интерактивная веб-реконструкция световой партии («Luce») из «Прометея»
Скрябина, ор. 60, поверх настоящей музейной фотографии 12 цветных ламп
(строка "тентелевского" светового органа). Один HTML-файл, без сборки,
без рантайм-зависимостей (кроме `@import` шрифтов Google — единственный
сетевой запрос; всё остальное, включая фото и теперь шрифт «Брокгауз и
Ефрон», встроено как base64).

## Два файла — какой редактировать

- **`luce.html`** — канонический исходник. Редактируй **только его**.
  Ссылается на `luce-photo.jpg` внешним `<img src="luce-photo.jpg">`.
- **`luce-standalone.html`** — генерируется из `luce.html` (фото
  встраивается как base64). Это то, что реально скачивает пользователь —
  явное требование: «сам скрябинизатор — одним файлом делай». **Не
  редактируй его руками** — после любых правок в `luce.html` пересобери:

  ```python
  import base64
  html = open('luce.html', encoding='utf-8').read()
  photo_b64 = base64.b64encode(open('luce-photo.jpg','rb').read()).decode('ascii')
  old = 'src="luce-photo.jpg"'
  assert html.count(old) == 1
  html = html.replace(old, f'src="data:image/jpeg;base64,{photo_b64}"')
  open('luce-standalone.html', 'w', encoding='utf-8').write(html)
  ```

  Затем отдавай пользователю **`luce-standalone.html`** — по умолчанию
  ожидается доставка одним файлом, каждый раз.

## Архитектура: два независимых режима, одна UI-оболочка

1. **«Прометея»** (`render()`, luce.html:1393) — жёстко заданная по
   партитуре реконструкция, тактовая точность, источник — массивы
   `stages` (luce.html:553) и `flashes` (luce.html:565), взятые из
   музыковедческих источников. Не меняются алгоритмом — это авторские
   данные, а не результат анализа.
2. **«Другая музыка»** (`renderAnalysisFrame()`, luce.html:914) — живой
   анализ произвольного аудио через цветовой круг Скрябина. Явно
   промаркирован как *не* историческая реконструкция, а лучшее
   приближение для случайного трека.

Оба вызываются только через **`renderCurrent(elapsed)`** (luce.html:1448) —
диспетчер по `analysisMode`. Это важно: раньше `resetBtn` и обработчик
клика по таймлайну звали `render()` (режим «Прометея») напрямую в обход
диспетчера, и при перемотке в «Другой музыке» показывались ярлыки вроде
`"Fis (возврат)"`. Если добавляешь новую точку, откуда меняется позиция
воспроизведения — **зови `renderCurrent`, а не `render`/`renderAnalysisFrame`
напрямую**.

## Ключевая архитектурная идея: activeColorMap — единственный источник истины

Для «Другой музыки» когда-то было два независимых анализа: офлайн-карта
всего трека (для таймлайна) и отдельный живой Гёрцель-анализ в реальном
времени (для фона/лампы). Они регулярно расходились — пользователь много
раз присылал скриншоты «фон и лампа не совпадают с полосой». Причина была
структурной: два разных прохода почти неизбежно дают разные ответы, сколько
их ни калибруй.

**Решение**: офлайн-карта (`buildColorMap()`, luce.html:761) считается один
раз сразу после загрузки файла и кладётся в `activeColorMap` /
`activeColorMapDuration`. И таймлайн (`paintTimelineFromColorMap()`,
luce.html:1375), и фон/лампа (`renderAnalysisFrame()` через
`colorMapSegmentAt()`, luce.html:657) читают **один и тот же** массив.
Разойтись они физически не могут. Живой анализ (`getFloatTimeDomainData` +
Гёрцель по сырому сигналу) используется **только** для того, чтобы решить
*когда* мигнуть дополнительной лампой (см. блок onset-детектора в конце
`renderAnalysisFrame`) — никогда для выбора «какого цвета» фон.

**Если в будущем задача снова окажется «фон/лампа не совпадают с
чем-то» — сначала проверь, не завёлся ли где-то второй независимый
источник цвета в обход `activeColorMap`.** Это самый частый класс багов
в этом проекте.

## Метод анализа: Гёрцель, не FFT-бины

И офлайн-карта, и (опосредованно) живой дисплей используют **алгоритм
Гёрцеля** (`goertzelMag()`, luce.html:742) по фиксированному набору целевых
частот `CHROMA_TARGET_FREQS` (luce.html:734, 4 октавы C2–B5, MIDI 36–83),
а не `AnalyserNode.getByteFrequencyData()`. Раньше живой путь был на
FFT-бинах, офлайн — на Гёрцеле; несмотря на «похожие» диапазоны частот, это
принципиально разные анализы и давали разные ответы на одном и том же
звуке. Если понадобится трогать частотный анализ — держи оба пути (если
они вообще снова станут два) на одном методе, либо (лучше) сохраняй текущую
схему с единственным источником истины.

`buildColorMap()` (luce.html:761): децимация к фиксированной **частоте**
~2600 Гц (не к фиксированному числу сэмплов — на длинных файлах это раньше
роняло Найквист ниже целевых частот), `segCount = clamp(40..180,
round(duration/3))`, топ-2 ноты на сегмент (порог `rel>=0.35`), затем
`mergeIntoStructuralRuns()` (luce.html:812) — мажоритарное сглаживание ±2 и
слияние коротких пробежек (`< max(2, round(n*0.04))`) с соседями.

## Максимум ламп и «динамика» — намеренно без пользовательских настроек

Максимум одновременных ламп = **2** (константа, без слайдера) — это
единственный документированный в партитуре дубль, «без выбора». Порог
чувствительности вспышек (`dynMultiplier = 3.0`, luce.html:1038) — тоже
константа, не слайдер. Пользователь явно попросил убрать оба UI-элемента
управления этим: строгая реконструкция по умолчанию не должна давать
пользователю «подкрутить» то, чего в оригинале не было. **Не возвращай эти
слайдеры**, если только пользователь прямо не попросит другого.

## Экран не гаснет (Android) — тройная защита, статус диагностики

Три независимых, дублирующих друг друга механизма (Android оказался
ненадёжен с одним Wake Lock):
1. **Screen Wake Lock API** — `requestWakeLock()`/`releaseWakeLock()`
   (luce.html:1259, :1271). Пишет строку состояния в `wakeLockState` на
   каждую попытку.
2. **Скрытое зацикленное `<video>`** (`#nosleepVideo`) — теперь
   полноэкранное, но спрятано за `.stage` (`z-index:-1`). **Важно**: этот
   `<video>` — прямой сосед `.stage`/`.vignette`, **не внутри `.wrap`**.
   `.wrap` имеет `position:relative;z-index:2`, создаёт свой stacking
   context и раньше «ловил» отрицательный z-index видео внутри себя, из-за
   чего видео рисовалось *поверх* `.stage`, а не позади — если увидишь
   «фон сломан» после манипуляций с версткой — проверь именно это первым
   делом.
3. **Media Session API** (`if('mediaSession' in navigator)`, luce.html:1234)
   — добавлен по прямому запросу пользователя («ютуб же не гаснет!»),
   регистрирует `play`/`pause` action handlers.

Живой статус всех трёх — в модалке `#modalBackdrop` (кнопка `?`),
`#wakeLockStatus`, заполняется при открытии модалки. **Не удалён и не
протестирован до конца** — см. «Открытые вопросы» ниже.

## Проверено эмпирически (не только «выглядит нормально»)

Методология, которую настойчиво требовал пользователь: генерировать
синтетическое «эталонное» аудио прямо из `stages`/`flashes`, прогонять
через реальное приложение (Playwright), сверять количественно с известным
правильным ответом — а не полагаться на визуальную проверку. Важный урок
по пути: первый эталон был сжат до 120 секунд вместо реальных ~22 минут и
дал обманчиво хорошую метрику (96.7% точности по кадрам) при **скрытом
мерцании** (37 смен ноты вместо 6 настоящих) — на реалистичной длительности
это вскрылось. **Если пишешь новый тест синтетическим эталоном — строй его
на реальной длительности трека, не сокращай для скорости**, либо явно
проверяй количество смен состояния, а не только процент правильных кадров.

Тестовые скрипты были в scratchpad конкретной сессии и **не сохранены в
репозитории** (это были одноразовые/итеративные debug-скрипты, не чистый
код продукта) — при необходимости пересоздать методологию с нуля, это
быстро (генератор WAV из `stages`/`flashes` через `soundfile`, прогон через
Playwright). **Важно про генерацию тестовых WAV**: Python-модуль `wave`
даёт файлы, которые `<audio>` проигрывает, но `AudioContext.decodeAudioData`
отклоняет (`EncodingError`) из-за нестрогого заголовка — используй
`soundfile`/libsndfile, он даёт спек-совместимые заголовки.

Финальная проверка перед хэндоффом: реальная запись Симфонии №1 ми мажор
Скрябина (загруженная пользователем) дала цветовую карту с доминантой «E»
(верно — тональность ми мажор) и правдоподобными отходами к D/H. Перемотка
на 6 разных позиций трека дала **согласованные** `stageName`/фон/лампу на
каждой позиции (тест на реальном файле, не синтетике).

## Исправлено: каскадное схлопывание цветовой карты на быстрой музыке

`mergeIntoStructuralRuns` мержил любой отрезок короче **4% от длины
трека** в соседний более длинный — на 22-минутном «Прометее» это ~53с
(нормально для его медленных стадий), но на 7-минутной симфонии — ~17с,
и реальная гармония меняется чаще: каждый неглавный отрезок проигрывал
гонку и поглощался, каскадом схлопываясь в 100% одну ноту на весь трек
(проверено на Симфонии №1 — до фикса все 144 сегмента показывали «E»,
хотя сырой посегментный анализ до сглаживания был богатым и музыкально
верным: E/H/A/Fis/D... с H — доминантой к E — на втором месте).

Фикс: порог теперь фиксированный **`MIN_RUN_SECONDS = 8`** (секунд,
не % от длины), luce.html:812-820. Проверено на обеих реальных записях
после фикса:
- Симфония №1: 144 сегмента → **21 содержательный блок** (E 29→H→As→
  Fis→E→C(8)→H→B→G(16, настоящий уход)→As→H→E→Fis→E→A→H→E→H→A→H→
  E(18, возврат к тонике)) — структура «тоника → уход → возврат»,
  музыкально осмысленно.
- «Прометей»: 180 сегментов → 26 блоков (было ~3 огромных). Начало
  C→G→Fis, конец — Fis(12), возврат сохранился. Не сломан.
Если снова понадобится трогать `MIN_RUN_SECONDS` — тестировать ОБЕ
записи, не только ту, что жалуется на данный момент — оба лежат в
`Скрябин - Complete Symphonies, etc. (Владимир Ашкенази)/CD1 - Symphony
No.1, Prometheus/` рядом с проектом (не в git — авторские записи,
пользователь держит их локально).

## Полноэкранный режим по таймеру/умолчанию — НЕ реализуемо буквально

Пользователь попросил включать fullscreen автоматически (по таймеру и/
или сразу при загрузке). Fullscreen API **требует user gesture**
синхронно в обработчике клика/тапа — ни `setTimeout`, ни автозапуск при
`load` браузер не пропустит (это не баг, а намеренное ограничение
безопасности во всех браузерах, обходов на клиенте нет). Единственный
реалистичный путь — вызывать `requestFullscreen()` прямо внутри
существующего обработчика клика по `playBtn` (клик — уже настоящий
user gesture), т.е. «полноэкранный включается, когда жмёшь Пуск», а не
буквально «по таймеру». **Не реализовано** — нужно подтверждение
пользователя, что это устраивает вместо буквальной просьбы.

   независимыми способами: офлайн-симуляция того же уравнения на полной
   длительности обеих настоящих записей (это дешевле, чем ждать реальный
   плейбек, и проверяет то же самое) + короткий живой прогон (реальное
   воспроизведение «Прометея», 35 сек). Найдено два отдельных бага:
   - **Кулдаун был математически no-op**: `now > analysisFlashUntil - 900`
     всегда истинно сразу после срабатывания (`analysisFlashUntil` — это
     `now + 260`, а `+260-900` — это прошлое). Заменено на честный дебаунс
     через отдельную `lastFlashTriggerTime` (luce.html:649, 973-979) с
     порогом 1000мс.
   - **`dynMultiplier=3.0` при быстрой EMA (0.9/0.1, luce.html:971) —
     скользящее среднее слишком быстро "догоняет" сигнал**, скачка в 3×
     почти никогда не остаётся: симуляция дала **0 вспышек за все 7 мин**
     на Симфонии №1 (Lento). Перебор параметров (>10 комбинаций,
     luce.html:962-980 содержит финальные числа и объяснение) показал
     жёсткий компромисс: то, что даёт вменяемую частоту на тихой
     симфонии, на плотном «Прометее» упирается в кулдаун и мигает
     механически каждую секунду; и наоборот. Выбран `dynMultiplier=2.4`,
     EMA 0.93/0.07 — на «Прометее» даёт чистые ~1.4 вспышки/мин, НЕ
     упираясь в кулдаун (значит это настоящие акценты, не потолок). **На
     тихой Lento-части Симфонии №1 всё ещё 0 вспышек** даже при щедрых
     параметрах — похоже, там просто нет достаточно резкой атаки для
     детектора относительной энергии; это не баг, а честный предел
     метода, не стал разгонять чувствительность дальше ради одной тихой
     записи ценой механического мигания на всём остальном.
4. **Вшитый нейродвижок для распознавания** (мега-задача пользователя:
   «швейцарский нож музыковеда» — несколько одновременных линий
   полифонии, контрапункт, додекафония, ритм) — кандидат:
   **Basic Pitch** (Spotify, открытый, полифонический, есть порт под
   TensorFlow.js) — НЕ проверены актуальный размер весов и лицензия в
   этой сессии, только по памяти. Веса — отдельным файлом (как музыка,
   не base64 в HTML) пользователь принял сам. Нерешённый конфликт:
   рантайм TensorFlow.js — это либо (а) вшить в luce.html (раздувает
   именно код), либо (б) грузить с CDN (новая сетевая зависимость сверх
   Google Fonts, ломает офлайн-сценарий на Android без связи, ради
   которого проект уже переделывал Wake Lock трижды). Пользователь также
   явно принял риск слабого ноутбука — производительность инференса в
   браузере на слабом железе нужно проверить на реальной модели ДО
   встраивания в основной UI, не после. Отдельная большая тема, требует
   своего захода — не начато.
   Дополнительно запрошено (тот же список, не проще предыдущего): стиль,
   эпоха/время написания, автор/композитор. **Важно не путать с Basic
   Pitch** — это модель для транскрипции высоты тона/нот, а не
   классификатор стиля/эпохи/автора; такая атрибуция — отдельная задача
   MIR (music information retrieval) своего рода, для неё нужна СВОЯ
   модель, и в отличие от Basic Pitch это не «скачал общеизвестное
   готовое решение» — авторство по аудио особенно ненадёжно даже в
   академических работах. Нужно отдельное исследование, есть ли вообще
   пригодная для браузера готовая модель, прежде чем на это рассчитывать.
   Также запрошено: распознавание инструментов (тембр) — та же оговорка,
   другая по типу модель, не Basic Pitch.

   **Как подходить к скоупу этой темы**: пользователь прямо сказал
   «пляшем от инструмента» — сначала посмотреть, что конкретная выбранная
   модель (Basic Pitch или другая) реально умеет на выходе, и уже от
   ФАКТИЧЕСКИХ возможностей строить список функций, а не заранее
   проектировать функции и потом искать модель под них. Список выше
   (додекафония, ритм, стиль/эпоха/автор, тембр, несколько линий
   полифонии/контрапункт) — это пожелания-ориентиры, не техзадание;
   ни одно из них не проверялось на предмет «а умеет ли это вообще
   какая-то существующая браузерная модель».

   **Именование файлов**: пользователь явно попросил НЕ называть файлы
   нейродвижка `luce*` — это отдельная ветка/линия работы, не замена
   текущему стабильному `luce.html`/`luce-standalone.html`. Когда дойдёт

   тех же файлов.

## Выбор цветовой модели («Другая музыка» — только там)

По прямому запросу пользователя добавлен селектор альтернативных
исторических систем цвето-звукового соответствия — `COLOR_MODELS`
(luce.html:642), UI в модалке статистики (`colorModelPicker`/
`colorModelSelect`), виден только в `analysisMode` (в «Прометее» скрыт —
`stages`/`flashes` держат авторские цвета Скрябина всегда, селектор на них
физически не влияет, см. `render()`).

**Исследовано МАКСИМАЛЬНО тщательно перед реализацией** (веб-поиск, не по
памяти) — включено то, для чего нашёлся реальный источник, честно
исключено то, для чего не нашёлся:
- **Скрябин** — уже был (`lampSpotsData`, измерено по реальному фото).
- **Римский-Корсаков** — Yastrebtsev 1908 через Galeyev & Vanechkina (2000)
  «Was Scriabin a Synesthete?» (Leonardo), сверено независимо с таблицей
  Сабанеева (совпадают C=белый, G=коричнево-золотой). Полная таблица на
  12 мажорных тональностей. Любопытный факт из источника: F и F# ОБА
  описаны как «зелёный, чистый (цвет зелени)» — не ошибка экстракции,
  подтверждено дважды независимыми запросами.
- **Кастель** (Clavecin oculaire, 1740, L'Optique des couleurs) — полная
  задокументированная хроматическая таблица на 12 полутонов, несколько
  академических источников сходятся.
- **Ньютон** (Opticks, 1704) — НЕ синестезия, математическая аналогия
  спектра с диатоническим ладом от D; определял только 7 естественных
  нот. 5 хроматических нот интерполированы НАМИ между соседями и явно
  помечены в коде как не принадлежащие Ньютону.
- **Римингтон** — сознательно НЕ включён: подтверждён только принцип
  («до = красный», далее по спектру пропорционально октаве) и два
  отдельных пункта (B=фиолетовый, A#=пурпурный) из вторичных источников,
  но полной таблицы 12 нот нигде найти не удалось — не стал додумывать
  9 недостающих значений и выдавать их за исторический факт.
- **Кандинский** — сознательно НЕ включён: его синестезия — это цвет↔тембр
  ИНСТРУМЕНТА (флейта/виолончель/труба...), а не цвет↔нота — структурно
  другая модель, не ложится в текущую архитектуру «12 нот → 12 цветов»
  без отдельной переделки.
- ~~🪩 Дискотека 80-х~~ — **УДАЛЕНА ПОЛНОСТЬЮ** позже в этой же сессии
  («фигня какая-то», прямая цитата) вместе со всем переключателем
  цветовых моделей. Больше не существует в коде (ни `disco80s` в
  `COLOR_MODELS`, ни `discoChaseEntries()`, ни UI). Абзац ниже про
  «упрощено до 2» — тоже устарел тем же коммитом, см. актуальное
  состояние в конце файла («Полифония/контрапункт — ФИНАЛЬНЫЙ дизайн»).

Hex-значения — НАША интерпретация словесного описания цвета из источника
(ни один источник 1908/1740/1704 года не даёт хекс-коды) — сама пара
«нота↔цвет» источникована, конкретный оттенок — наше лучшее прочтение.

**Архитектурная деталь, которая иначе кажется багом**: свечение самой
лампы на фото — это CSS custom property `--sc`, выставляется ОДИН раз при
построении DOM (было — `lampSpotsData[].c` напрямую), не читается CSS
динамически из `colorByNote`. Добавлена `refreshLampSpotColors()`,
вызывается из `applyColorModel()` при каждом переключении — без неё лампа
на фото осталась бы всегда скрябинской, а менялся бы только фон/таймлайн,
что выглядело бы как наполовину сломанная функция.

**Реальный баг, пойманный до прогона, не после**: изначально селектор
инициализировался вызовом `applyColorModel('scriabin')` сразу при
определении — но внутри функции есть `if(analysisMode)`, а
`analysisMode` объявлена через `let` НИЖЕ по файлу (temporal dead zone) —
это бросило бы `ReferenceError` при каждой загрузке страницы. Исправлено
прямой инициализацией `colorByNote` без вызова полной функции на этом
этапе (luce.html:706-712) — `applyColorModel()` в её полном виде вызывается
только позже, из пользовательского взаимодействия, когда весь скрипт уже
инициализирован. Урок общий: **порядок объявления `let`/`const`
относительно места первого вызова — проверять всегда, особенно когда
новый код вызывается eagerly (не из обработчика события) рядом с началом
скрипта**, не полагаться на то, что «раз функция похожа на предыдущие -
она отработает так же».

Проверено вживую: переключение между всеми 4 моделями меняет фон, лампу
на фото, таймлайн и цитату источника мгновенно; возврат к «Прометею»
(даже с активной не-Скрябинской моделью) показывает исключительно
авторские цвета — подтверждено, не только прочитано в коде.

**Смежный баг, найденный по пользовательскому отчёту**: при переключении
с «Другой музыки» (особенно с 🪩 диско — сразу несколько ламп) на
«Прометея» старое визуальное состояние (лампы/фон) могло держаться до
срабатывания `loadedmetadata` у нового `<audio>` — выглядело как «режим
не переключился». Исправлено в `loadTrack()` (luce.html, начало
функции): немедленный сброс `setLampAmbientMulti([])`/`setLampFlash(null)`/
`tintFlash`/`discHolder.glow` при загрузке ЛЮБОГО трека, плюс немедленный
`render(0)` в ветке «Прометея» (не ждать `loadedmetadata` — `elapsed=0`
делает `frac=0` независимо от того, что `durationSec` на этот момент ещё
старое). Проверено прогоном (диско → «Прометей» несколько раз подряд).

## luce-plus — нейродвижок (файл, не ветка — см. ниже почему)

Отдельная линия работы по прямому запросу пользователя — распознавание
через настоящую нейросеть (Basic Pitch), НЕ на основной `luce.html`/

пользователя: файлы нейродвижка НЕ называть `luce*`... кроме
самого имени продукта `luce-plus`, которое он сам и предложил).

**Важно про ветки — урок этой сессии.** Изначально эта работа шла в
отдельной ветке `claude/luce-plus-neural-engine`. Пользователь и я
работаем в ОДНОЙ И ТОЙ ЖЕ рабочей папке на диске (не разные клоны) — при
переключении веток файлы, закоммиченные только в одной из них, физически
пропадают с диска. Пользователь пытался открыть `luce-plus.html`, пока я
(в рамках той же сессии) переключился обратно на основную ветку — файл
исчез из папки, это выглядело как поломка, хотя ничего не терялось (всё
было в git). **Решение**: ветка `claude/luce-plus-neural-engine` слита
обратно в `claude/scriabin-museum-prometheus-sks4l2` — теперь ОДНА
рабочая ветка, все файлы видны одновременно всегда. Пользователь также
явно попросил **версионировать экспериментальные файлы номером в самом
имени** (`-v1`, `-v2`...), а не полагаться на git-ветки как на способ

экспериментальных файлов в этом проекте. `luce.html`/`luce-standalone.html`
остаются БЕЗ номера версии — это не эксперимент, а основной продукт,

**Если снова понадобится изолировать рискованную работу — НЕ переключай
ветку в этой же рабочей папке, пока пользователь может одновременно
трогать файлы; либо работай в отдельном git worktree, либо просто новым
версионированным файлом на той же ветке.**

### Что сделано и подтверждено прогоном

1. **Ветка создана** от `claude/scriabin-museum-prometheus-sks4l2`.
2. **`luce-plus-v1.html`** = копия `luce.html` на момент создания ветки —
   отправная точка, ещё не редактировалась содержательно.
3. **Движок собран и встроен** — `@tensorflow/tfjs` + `@spotify/basic-pitch`
   (оба Apache-2.0, лицензия подтверждена напрямую из `package.json`, не
   по вторичным источникам) собраны в один IIFE-бандл через esbuild
   (одноразовый шаг сборки, выполнен НЕ в проекте, а во временной
   scratch-папке с `npm install` + `npx esbuild entry.js --bundle
   --format=iife --minify --target=es2018` — сам проект как был без
   node_modules/package.json, так и остался). Результат — 2.3 МБ
   (595 КБ gzip) — вставлен ЦЕЛИКОМ inline в `<script id="luce-plus-
   engine">` внутри `luce-plus-v1.html`, экспортирует
   `window.LucePlusEngine = {tf, BasicPitch, outputToNotesPoly,
   addPitchBendsToNoteEvents, noteFramesToTime}`. Если бандл нужно
   пересобрать — команда та же, `entry.js` тривиальный (5 строк,
   реэкспорт + присвоение на `window`), воспроизвести легко, сам файл
   `entry.js` в этой сессии не сохранён в репозитории (был в scratch).
4. **Веса модели** — `model/model.json` + `model/group1-shard1of1.bin`
   (0.71 МБ), скопированы из `node_modules/@spotify/basic-pitch/model/`
   пакета версии 1.0.1, лежат в репозитории рядом с `luce-plus-v1.html`,
   НЕ в base64 — ровно то разделение, о котором просил пользователь.
   **Загружаются через файловый пикер** (кнопка «🧠 Загрузить модель Basic
   Pitch», luce-plus-v1.html, рядом с `fileInputOther`), **не через
   `fetch()`** — первая версия делала `new BasicPitch('./model/model.json')`,
   а `BasicPitch` внутри дёргает `tf.loadGraphModel(url)` → `fetch()`, что
   `file://` блокирует насмерть («Failed to fetch», подтверждено
   пользователем на скриншоте реального использования). Пикер читает
   `model.json` + `.bin`-шард(ы) как обычные `File` (как музыку), при
   мультивыборе сопоставляет `.bin`-файлы с `model.json.weightsManifest[0].paths`
   **по имени, не по порядку выбора** (ОС не гарантирует порядок), склеивает
   в один `ArrayBuffer` и собирает модель через `tf.io.fromMemory({modelTopology,
   weightSpecs, weightData})` → `tf.loadGraphModel(handler)` — ни разу не
   обращаясь к сети или диску напрямую. Результат (`Promise<GraphModel>`)
   передаётся в `new BasicPitch(тотПромис)` — конструктор прямо поддерживает
   оба варианта (строка-путь ИЛИ уже загруженный промис), см. `types/inference.d.ts`
   пакета. **Промежуточная идея (base64-встраивание весов прямо в HTML)
   была начата и брошена** — пользователь сам поправил: движок встраивать,
   модель грузить файлом, как музыку, не через base64.
5. **Инференс прогнан на РЕАЛЬНОМ аудио** (15-секундный срез Симфонии
   №1) и дал корректный результат: 447 нот, реальные MIDI-высоты
   (диапазон 40–73, разные регистры одновременно — настоящая
   полифония), тайминги, амплитуды. Пайплайн `evaluateModel()` →
   `outputToNotesPoly()` → `addPitchBendsToNoteEvents()` →
   `noteFramesToTime()` работает end-to-end, не только теоретически по
   документации.

### Найдено по пути (не в документации — прогоном)

- **Модель требует ВХОД РОВНО 22050 Гц**, иначе кидает исключение
  (`Input audio buffer is not at correct sample rate!`) — decodeAudioData
  в браузере обычно даёт нативную частоту файла (у наших записей —
  48000). Нужен ресемплинг через `OfflineAudioContext(1, ceil(dur*22050),
  22050)` + `createBufferSource` + `startRendering()` ПЕРЕД вызовом
  `evaluateModel` — без этого шага не работает вообще, не «работает
  плохо».
- **TF.js регистрирует webgl-ядра дважды** (десятки предупреждений
  `kernel already registered` в консоли) — судя по всему, и наш прямой
  `import * as tf`, и внутренний импорт `tf` из `@spotify/basic-pitch`
  оба попадают в бандл. Не ошибка (TF.js это допускает, использует первую
  регистрацию), но шумно и указывает, что бандл не дедуплицирован —
  реальная возможность уменьшить итоговый размер (не делал, не было
  на это времени в рамках сессии).

### Скорость — ИСПРАВЛЕНО, первое измерение было артефактом

**Первоначальное измерение было ложной тревогой.** Изначально записано
здесь: «109 секунд на обработку 15 секунд аудио (7.3x медленнее
реального времени)», с оценкой «~2.6 часа на весь Прометей». Это
число **не подтвердилось** при перепроверке и, вероятно, было
испорчено окружением: тот прогон случился в браузерной вкладке, уже
использованной для десятков предыдущих тестов в той же сессии (тензоры
TF.js не освобождались явно между прогонами — вероятная утечка
GPU-памяти/контекста WebGL, деградирующая именно повторные инференсы в
долгоживущей вкладке).

**Перепроверено дважды, на СВЕЖЕЙ странице каждый раз, на двух разных
записях** (после перехода на загрузку модели через файловый пикер —
см. ниже):
- Симфония №1: 20с аудио → 5.2с обработки, **0.3x реального
  времени** (то есть быстрее реального времени примерно втрое) —
  оценка на весь трек (432с) ~1.9 мин.
- «Прометей»: 20с аудио → 6.2с обработки, тоже **0.3x** — оценка на
  весь трек (1302с) ~6.7 мин.

Одинаковое отношение на двух непохожих записях — сильный сигнал, что
0.3x это реальная характеристика модели в этом окружении (backend
webgl), а не случайность. **Всё ещё не проверено на реальном железе
пользователя** — но теперь ожидания реалистичные (единицы минут на
трек, не часы), и сама фича похоже жизнеспособна.

**Урок методологии**: при замере производительности что-либо в TF.js —
использовать СВЕЖУЮ страницу/вкладку для каждого замера, не переиспользовать
долгоживущую сессию с историей множества предыдущих прогонов. Если результат
сильно расходится с ожиданиями (в любую сторону) — перепроверить на чистом
старте, прежде чем записывать как факт.

### Полифоническая визуализация — ПЕРВАЯ ВЕРСИЯ (архив, дизайн сменился)

**УСТАРЕЛО** — этот раздел описывает whole-track пианоролль,
который пользователь потом отклонил («ничего не даёт»). Актуальный
дизайн — «Полифония/контрапункт — ФИНАЛЬНЫЙ дизайн» в конце файла.
Оставлено здесь ради находок, которые СОХРАНИЛИСЬ в актуальной версии
(WebGL-краш на целом треке и его причина, метод анализа через
`evaluateModel`/`outputToNotesPoly` и т.д.) — сам UI (`lucePlusPanel`,
`lucePlusPianoRoll`, whole-track `runLucePlusAnalysis`) в текущем коде
уже не существует в таком виде.

Пианоролль: `<canvas id="lucePlusPianoRoll">` в `lucePlusPanel`, функция
`drawLucePlusPianoRoll()` — x = время, y = высота (MIDI 21–108), одна
горизонтальная полоска на ноту, цвет по ноте через ТУ ЖЕ `colorByNote`
(уважает выбранную цветовую модель, включая 🪩 диско). Обновляется
**инкрементально** по ходу анализа (см. ниже про чанки), не только в
конце — прямой ответ на вопрос пользователя «можно ли на лету».

**Честно: это НЕ контрапункт.** Basic Pitch отдаёт мешок нот
(высота+время+громкость+pitch bend), БЕЗ разметки «какая нота какому
голосу принадлежит». То, что нарисовано — это все ноты сразу, видно
полифонию (несколько одновременных линий), но не разделение на
самостоятельные голоса. Разделение на голоса (voice separation /
streaming) — отдельная, не начатая задача: кластеризация нот в
непрерывные линии по близости высоты и времени. Пользователь спросил
прямо («контрапункт?») — ответ дан честно, не выдавать одно за другое.

Успешный прогон на полном треке: Симфония №1 (7 мин, реальный файл) →
**17314 нот за 270с (0.63x реального времени)**, картинка результата
показывает настоящую плотную полифоническую структуру, коррелирующую
со структурой симфонии (сохранена как референс при подготовке этой
заметки, не в репозитории — просто скриншот для отчёта пользователю).

**Два бага, найденные и (частично) исправленные по пути:**

1. **`Failed to compile fragment shader` на полном треке** — `evaluateModel()`
   на ВЕСЬ трек сразу падал с этой ошибкой ещё ДО первого чанка (canvas
   оставался абсолютно пустым). Причина (гипотеза, не подтверждена на
   100%, но исправление работает): `prepareData()` внутри basic-pitch
   делает `tf.signal.frame()` на ВЕСЬ буфер разом, создавая один
   тензор со всеми ~2-секундными окнами трека — для многоминутного
   трека это тензор, который правдоподобно превышает максимальный
   размер WebGL-текстуры на данном GPU. **Исправлено**: вместо одного
   вызова `evaluateModel()` на весь трек — цикл по 30-секундным кускам,
   каждый в своём `OfflineAudioContext`/`evaluateModel()`, тайминги нот
   сдвигаются на смещение куска (`n.startTimeSeconds += chunkStart`).
   Заодно даёт более частые обновления пианоролля (раз в кусок, не раз
   в чанк-внутри-evaluateModel).
2. **Утечка тензоров/памяти, НЕ исправлена, только обойдена размером
   чанка.** `tf.memory().numTensors` растёт монотонно на протяжении
   ОДНОГО прогона (248 → 2676+ за 7-минутный трек), `numBytes` — с
   единиц МБ до ~385МБ. Симптом: скорость заметно деградирует к концу
   одного прогона (первый 30-секундный кусок — реального времени
   быстрее почти в 3 раза; последние куски — заметно медленнее, отсюда
   итоговые 0.63x вместо изначальных ~0.3x на коротких пробах).
   Библиотека `@spotify/basic-pitch` не оборачивает внутренние тензоры
   в `tf.tidy()` (проверено чтением `esm/inference.js` — `evaluateSingleFrame`
   возвращает сырые тензоры без явного диспоуза после `.array()`).
   **Не чинил** — не было времени в рамках сессии; если станет
   проблемой (падение на очень длинных треках или слишком медленно) —
   следующий шаг: обернуть каждый вызов `evaluateModel` (или каждый
   `evaluateSingleFrame` внутри, если получится патчить/обернуть) в
   `tf.tidy()`/`tf.engine().startScope()`+`endScope()`, либо звать
   `tf.disposeVariables()`-подобную очистку МЕЖДУ кусками (не между
   переменными модели — их трогать нельзя, только промежуточные
   результаты).

### Полифония/контрапункт — ФИНАЛЬНЫЙ дизайн: прямо на лампах, без переключателя

История решения (важно понимать ПОЧЕМУ, не только ЧТО, если снова
захочется что-то менять здесь) — прошло несколько итераций за одну
сессию, каждая по прямой обратной связи пользователя:
1. Статичный пианоролль на ВЕСЬ трек — отклонено («мне это ничего не
   даёт», «всю запись не имеет смысла обсчитывать»).
2. Отдельный canvas «Полифония» с 2 линиями (верх/низ) + переключатель
   «Цветовой круг / Полифония» — работало, но пользователь пришёл к
   выводу, что переключатель не нужен: «у Скрябина вторая лампа
   загорается редко, потому что это не полифония, а у Баха несколько
   ламп должны загораться» — то есть ПРАВИЛЬНОЕ место для полифонии —
   это САМИ лампы, не отдельная картинка.
3. **Финал**: полифония и контрапункт показываются НА САМИХ лампах
   Скрябина, без переключателя, без отдельного canvas. Реализовано в
   luce-plus-v1.html, JS-объект `renderAnalysisFrame` переопределён
   поверх оригинала (переопределение работает, т.к. в luce.html это
   `function`-декларация, не `const` — совместимо с `var`-подобным
   переприсваиванием).

**Как это устроено:**
- **Скользящее окно ±10с вокруг текущей позиции воспроизведения**, НЕ
  весь трек. `refreshLucePlusWindow(centerTime)` — один `evaluateModel()`
  на маленький срез (~20с), пересчитывается заново, когда `posSec`
  отъезжает от центра последнего анализа больше чем на 8с
  (`CP_REFRESH_THRESHOLD`). Анализ занимает несколько реальных секунд
  (~0.3-0.6x по замерам в этой сессии), поэтому окно НЕИЗБЕЖНО чуть
  отстаёт от живого плейхеда — осознанный компромисс, не баг.
  Побочный эффект: маленький срез (~20с) заодно обходит стороной баг
  «Failed to compile fragment shader» на целом треке (см. ниже) — не
  специально чинили, но чинится сам собой при таком размере входа.
- **Несколько ламп одновременно** = реальные одновременно звучащие ноты
  из окна (`lucePlusActiveNotesAt(t)`), не одна доминирующая нота, как
  раньше. Один моноголосный пассаж — одна лампа (как и должно быть).
  Двойные ноты/настоящая полифония — несколько ламп сразу.
- **Яркость лампы** = громкость ноты (`amplitude`), а если НЕСКОЛЬКО
  одновременных нот попадают на один и тот же тон в разных октавах
  (`setLampAmbientMulti` физически не различает октавы, ключ — только
  12 тонов) — лампа не просто "теряет" одну из нот молча, а горит
  **ЯРЧЕ** (прямой запрос пользователя: «если в октаву — лампа должна
  ярко гореть»). Формула: `intensity = min(1, ампл1 + 0.35*ампл2 + ...)`
  — проверено синтетическим юнит-тестом: 1 нота → 0.60, та же нота
  задвоенная октавой → 0.81.
- **Контрапункт = вспышка/подсветка `tintFlash`**, три класса событий
  (`lucePlusEventAt(t)`), из которых первые два — по идее второго ИИ
  (Qwen, см. ниже), адаптированные под точные онсеты Basic Pitch:
  - **«Опора»** (золотая, `#ffd65a`) — приход на чистый консонанс
    (унисон/квинта/октава, интервал mod 12 ∈ {0,7}) ИМЕННО в момент
    атаки одной из нот (окно 180мс), не просто случайно висящий
    интервал — иначе вспыхивало бы на любом удержанном созвучии.
  - **«Вступление»** (голубая, `#78dcff`) — новая нота атакует, пока
    хотя бы одна другая уже звучит — как начинаются имитации/фуги.
  - **Встречное движение** (белая, `#ffffff`) — крайние голоса (самый
    высокий и самый низкий звучащие тона) идут в противоположные
    стороны — один из 4 классических видов контрапунктического
    движения (наряду с прямым/параллельным/косвенным), не придуманная
    эвристика.
  Общая функция `lucePlusEventAt()` используется один раз, никакого
  риска второго независимого источника «что сейчас происходит» (тот
  самый класс багов, о котором предупреждает секция про
  `activeColorMap` выше).
  **Конфликт, о котором стоит знать**: `tintFlash` — тот же элемент,
  что использует ОРИГИНАЛЬНЫЙ онсет-детектор для второй лампы (см.
  «Найдено: второй раз багов у второй лампы» ниже) — при активном окне
  анализа новая логика может перебивать старую на том же кадре. Не
  чинили — оба события достаточно редкие, чтобы конфликт был
  практически незаметен, но это не 100% строго, если понадобится точность.
- **Прометей не затронут**: весь этот код живёт только в проверке
  `analysisMode` (= «Другая музыка»), и только пока есть данные
  скользящего окна. Авторские `stages`/`flashes` Скрябина как были, так
  и остаются нетронуты.

**Проверено на реальных файлах, не только рассуждением:**
- Партита №1 Баха для скрипки соло (Corrente e Double, Леонид Коган,
  пользователь сам положил специально для теста): на t≈148.75с —
  РЕАЛЬНАЯ чистая квинта D+A, обе лампы загорелись одновременно, золотая
  вспышка «опоры» сработала ТОЧНО в этот момент. Раньше (при первой,
  полнотрековой версии) — 2991 нот за 83.3с (0.29x) на весь трек с
  прежним дизайном линий, картинка показывала ожидаемый для соло-скрипки
  паттерн (унисон/расхождение на двойных нотах) — тот прогон архивный,
  дизайн с тех пор сменился, но подтверждает, что данные Basic Pitch на
  этом материале в принципе музыкально осмысленны.
- Синтетический юнит-тест на прямое присваивание `lucePlusWindowNotes`
  (C4+C5 одновременно) — яркость лампы «C» 0.60 → 0.81 при добавлении
  октавного дубля, подтверждает формулу выше напрямую, а не только по
  логике кода.

**Честно не сделано / упрощения:**
- **Пересечение голосов** (voice crossing, третья идея Qwen) — НЕ
  реализовано. Требует персистентного ID голоса через время (чтобы
  понять, что «верхний» голос физически стал «нижним», а не просто
  чья-то ещё нота оказалась выше) — у Basic Pitch нет голосовых меток
  вообще, а моя логика «топ/боттом по рангу на каждый момент» этого не
  даёт, ранг всегда отсортирован. Настоящее отслеживание голосов —
  отдельная, не начатая задача (нужен алгоритм вроде "streaming" —
  склейка нот в непрерывные линии по близости высоты/времени).
- **Ответ на вопрос «6-голосная фуга = 6 ламп?»**: НЕ обязательно — лампа
  одна на ТОН (12 штук), не на голос. 6 голосов на 6 разных тонах = 6
  ламп. Но октавные дубли (частые у Баха, особенно в кадансах) схлопнут
  часть голосов на одну и ту же лампу — реалистичнее 3-6 ламп в
  зависимости от РЕАЛЬНОГО числа разных тонов в моменте, не от числа
  голосов буквально. Так же устроен и сам физический орган Скрябина.
- Второй опыт Qwen (по визуализации, второе сообщение пользователя с его
  идеями) также предлагал «нити» голосов с постоянной идентичностью и
  «перемычки» между ними при консонансах — тоже требует персистентного
  трекинга голосов, не реализовано по той же причине.
- `renderAnalysisFrame = function(){...}` — переопределение поверх
  оригинала; если основной luce.html когда-то изменит саму реализацию
  этой функции, обёртку в luce-plus придётся синхронизировать вручную.

с реальной тональностью произведения (это буквально в названии файла).

### Ответ на «что нам этот ИИ даёт» — не отвечено вовремя, отвечено здесь

Текущий Гёрцель-анализ (`buildColorMap`, «Другая музыка») даёт **одну
доминирующую ноту на момент времени** — это в принципе не может
показать полифонию, только последовательность одиночных цветов. Basic
Pitch даёт **все одновременные ноты** с высотой/таймингом/громкостью/pitch
bend — качественно другой тип данных, не просто «точнее», а «показывает
то, что Гёрцель не может показать в принципе» (несколько голосов сразу).
Это основа для: (уже есть) пианоролль-визуализация полифонии; (не
начато) разделение на голоса/контрапункт, додекафония, ритм,
стиль/эпоха/автор — все эти пункты ТРЕБУЮТ этого же выхода модели как
сырья, ни один не работает на выходе Гёрцеля.
