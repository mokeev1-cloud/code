# Мастер PQ — документация для разработчика (и для Claude)

Встроен в `pq-master.html` (блок `pqm-dev-docs`). Цель — чтобы доработка читала один-два модуля,
а не весь файл (~1 МБ).

## Что это

Один автономный HTML-файл для работы с Power Query (язык M) в книгах Excel / Power BI:
редактор, оптимизатор с автоисправлениями, песочница-интерпретатор, NDA-шлюз (обезличивание
для ИИ и обратная подстановка), запись исправленной книги. Всё работает в браузере, **сеть
запрещена CSP**. Пользователь работает на десктопе, интерфейс на русском.

## Инварианты (нарушать нельзя)

- **Никакой сети.** CSP `default-src 'none'; connect-src 'none'`. Никаких `fetch`/XHR/WebSocket/CDN.
  Все библиотеки встроены (CodeMirror — `vendor/`). Шрифты только системные.
- **Всё, что уходит наружу обезличенным, — через `gate()` + `audit()`** (`app/ui-base.js`).
  В автоматике (агент) — `gate(…, { noOverride: true })`.
- **Словарь замен и оригиналы никогда не пишутся в папку обмена** (`nda/agent.js`).
- **Содержимое листов книги не читается.** Читается только DataMashup и метаданные запросов.
- **Код книги меняется только через `setWork(text, src, label)`** (`app/state.js`), чтобы правка
  попала в историю и все виды обновились.
- **Неизменённые части книги переносятся байт в байт** (`core/zip-mashup.js`): своя реализация ZIP
  копирует сжатые данные как есть. Самотест проверяет побайтную идентичность.
- Любые данные в `innerHTML` — только через `escHtml()`. Ответы агента и файлы — недоверенные данные.
- В IndexedDB — только ссылки на файлы (`FileSystemFileHandle`), не содержимое.

## Файлы и сборка

Всё нужное для разработки встроено в сам HTML; папка `pq-master/` в репозитории — его разрезанная копия.

| Путь | Где в HTML | Что это |
|---|---|---|
| `src/html`, `src/css`, `src/js` | разметка, `<style>`, блок `pqm-app` | модули приложения |
| `DEV.md` | блок `pqm-dev-docs` | этот документ (Справка → «Для разработчика») |
| `build.mjs` | блок `pqm-dev-files` | сборщик и разрезчик, без зависимостей (Node ≥ 18) |
| `test/e2e.mjs`, `test/stress.mjs` | блок `pqm-dev-files` | сквозной прогон в браузере; стресс-проверки ядра |
| `vendor/codemirror.entry.js` | блок `pqm-dev-files` | точка входа сборки CodeMirror |
| `vendor/codemirror.bundle.js` | блок `pqm-vendor` | CodeMirror 6 (MIT), уже собран |

**Есть только HTML.** Справка → «Для разработчика» → «⬇ build.mjs», затем
`node build.mjs --split pq-master.html pq-master` — восстановятся все исходники, тесты и сам сборщик.
Для чтения хватит оглавления в начале HTML: номера строк каждого модуля.

```
node pq-master/build.mjs            # собрать ../pq-master.html
node pq-master/build.mjs --check    # + разрезка восстанавливает все модули байт в байт
node pq-master/test/e2e.mjs         # headless Chromium: самотест + сценарии UI (нужен playwright-core)
node pq-master/test/stress.mjs      # фаззинг ядра, утечки, библиотека M, битые файлы, скорость (только Node)
```

Порядок модулей задаёт `MANIFEST` в `build.mjs`; новый файл добавляйте туда. Модули типов `js`,
`vendor`, `file` не должны содержать закрывающий тег script и начало HTML-комментария (сборщик
проверяет) — такие строки собирайте из частей: `'<' + '/script>'`.

Встроенный самотест (раздел «Самотест» или `runSelfTest()` в консоли) должен проходить полностью.
Он создаёт тестовую книгу в памяти, прогоняет её через все модули и сохраняет/восстанавливает `S`.

**Размер.** Сейчас ~1 МБ: CodeMirror ~400 КБ, интерпретатор ~90 КБ, справочник функций ~57 КБ,
самотест ~40 КБ, файлы разработки ~40 КБ. Новые данные — компактными строками, не JSON-объектами;
не встраивайте то, что можно вычислить. Пересборка CodeMirror почти ничего не даёт: неиспользуемые
экспорты — внутренние части ядра, которые попадают в бандл в любом случае. Если версию всё же надо
обновить:

```
npm i @codemirror/state@6 @codemirror/view@6 @codemirror/language@6 @codemirror/commands@6 \
      @codemirror/autocomplete@6 @codemirror/search@6 @codemirror/lint@6 @lezer/highlight@1 esbuild
npx esbuild vendor/codemirror.entry.js --bundle --format=iife --minify --target=es2019 \
      --legal-comments=none --outfile=vendor/codemirror.bundle.js
```

## Поток данных

1. Файл → `loadBookFromBytes` → объект `book` (`origSection` — текст Section1.m, `meta` — метаданные запросов).
2. `setBook` → `initBookState` → `S.work = origSection` → `reanalyze()`:
   `analyzeSection` → `lintSection` → `optimizeSection` → `emitState('book')`.
3. Виды подписаны через `registerView(id, { render(reason), onShow() })`. Активный вид
   перерисовывается при каждом `emitState`, остальные — при показе.
4. Любая правка (редактор, оптимизатор, ИИ, рефакторинг, сниппет) → `setWork(новыйТекст, источник, подпись)`.
5. Сохранение: `buildBookWithSection(S.book, S.work)` → контрольное чтение → запись (копия или оригинал).
6. Обезличивание считается лениво: `ensureAnon()` (`views/anon.js`) по ключу «рабочая версия + настройки».

## Рецепты

**Новое правило линтера/оптимизатора.** Эвристику — в `lintSection` (`opt/lint.js`): `add(sev, rule, query, step, msg, fix)`.
Карточку с автоисправлением — в `optimizeSection`: ветка `case 'rule':` или собственное правило ниже.
Исправление — чистая функция `fix(text, opts) → новыйText`, считающая позиции **по тому же тексту**, на
котором построен анализ (`A`). Обязательно задайте `safety`: `safe` — только если результат запроса
гарантированно не меняется. Если исправление меняет другие запросы или добавляет/удаляет запросы,
впишите правило в `NONLOCAL_FIX_RULES`: остальные «Применить все безопасные» применяет пачкой — по
одному на запрос за проход. Добавьте проверку в самотест: фикс даёт корректный синтаксис, а для
`safe` — тот же результат в песочнице (см. проверку «безопасные исправления не меняют результат»).
Всё, что считается на каждую отрисовку, — линейно по размеру книги (`candidatesOf` в оптимизаторе).

**Новая функция в справочник.** Строка в `M_REF_SRC` (`m/reference.js`). Если её можно вычислять,
добавьте реализацию в `MLIB` (`m/interp.js`) через `def(имя, (a, b) => …)` — аргументы приходят
вычисленными, `force()` раскрывает ленивые значения, ошибки — `throw new MErr(reason, message)`.

**Новый сниппет.** Объект в `SNIPPETS` (`opt/snippets.js`): `fields` + `gen(values) → M-код`.
Самотест сам проверит, что код разбирается.

**Новый раздел интерфейса.** `src/html/view-xxx.html` (`<section class="view" id="view-xxx">`),
`src/js/views/xxx.js` с `registerView('xxx', …)`, пункт в `NAV` (`app/shell.js`), оба файла — в `MANIFEST`.
Для разделов, требующих книгу: обёртка `.hasbook` и сообщение `.needbook-msg`.

**Новая тема.** Блок `[data-theme="id"]{…}` в `css/themes.css` (переопределить токены из
`theme.css`, при необходимости — отдельные компоненты) и строка в `THEMES` (`app/shell.js`).
Тема хранится в настройках; без атрибута `data-theme` действует системная светлая/тёмная.

**Подсказка раздела.** Текст в `HINTS[id]` (`app/hints.js`). Закрытые подсказки помнятся в
`localStorage`; «Показать подсказки снова» — в настройках и палитре.

**Новая категория обезличивания.** `CATS` в `nda/anon.js` + классификация в `anonymizeM`
(контекст строкового литерала: функция/аргумент, поле записи, сравнение). Метка `⟦CAT_N⟧` — заглавные латинские буквы.
Строки, привязанные к именам (`Сервер = "…"` в шаге, запрос-строка, параметр с `meta`), классифицируются
по месту использования имени в аргументе функции-источника (`binds`/`useLocal`/`useGlobal`, `paramStr`);
поля записей-настроек — по имени поля (`FIELD_ROLES`). Новую конструкцию добавьте в генератор утечек
`test/stress.mjs`.

## Методология проверки

- Синтетический эталон > визуальная проверка. Самотест строит книгу с известными секретами
  и проверяет количественно: секреты не утекли, обратная подстановка побайтна, файл после сборки
  читается тем же кодом, CRC всех частей верны.
- Для оптимизатора — семантическая проверка интерпретатором: результат до и после «безопасных»
  исправлений совпадает.
- Внешняя проверка: `test/e2e.mjs` дополнительно открывает собранную книгу через Python `zipfile`.
- Стресс: `test/stress.mjs` грузит ядро в Node и проверяет свойства на тысячах случайных входов —
  анализ не падает на незаконченном коде, обезличивание обратимо побайтно и не пропускает секреты
  в 25 типичных конструкциях, функции интерпретатора дают только ошибки M, битые .xlsx — понятные
  сообщения. Найденный класс ошибок закрепляйте проверкой в самотесте.
- Скорость меряйте на большой книге (`stress.mjs` строит ~3800 строк): всё, что вызывается на
  каждую отрисовку или правку, должно быть линейным по размеру книги.
- Не проверено автоматически: открытие собранной книги в настоящем Excel / Power BI Desktop
  (в контейнере их нет). Если пользователь сообщает о проблеме открытия — начинайте с
  `core/zip-mashup.js` (`buildBookWithSection`) и сравнения частей ZIP.
- В headless-Chromium контейнера без UTF-8 локали кириллические имена скачиваний превращаются
  в `download` — это окружение, не баг (с `LANG=C.UTF-8` всё корректно).

## Известные ограничения и следующие шаги

- Интерпретатор — подмножество M: нет свёртки, нет источников, часть функций отсутствует;
  числа — double. Новые функции легко добавлять в `MLIB`.
- Линтер, оптимизатор и карта тяжести — эвристики по тексту; реальное время даёт только
  загруженная диагностика Power Query.
- .pbix нового формата (запросы в модели VertiPaq) не читается; запись Power BI экспериментальная.
- **Целевой сценарий пользователя**: управленческий учёт группы компаний на выгрузках 1С (БП и
  самописные) + таблицы Excel, маппинг статей, разметка по ЦФО и проектам; обновление ~1 час, цель —
  ускорить на порядок. Под него в `opt/lint.js` правила: `row-lookup` (поиск в справочнике внутри
  функции для каждой строки; находит `rowLookups`; исправление — слияние через `lookupShape` или
  буфер), `list-buffer` и `buffer-in-each` (вычислить один раз отдельным шагом — `bufferFix`),
  `join-buffer`, `multi-eval` (сколько раз запрос вычисляется за «Обновить всё» — `refreshReads`,
  на карте тяжести «×N»), `folder-combine`, `useless-sort`, `manual-mapping`, `excel-settings`
  (совет уровня книги, оценку не снижает). Самотест проверяет на данных в песочнице, что слияние и
  буферы не меняют отчёты. Дальше — по обезличенному пакету и диагностике с реальной книги.
- Не реализовано (сознательно): смена режима загрузки запросов («Только подключение») прямо в книге —
  это правка connections.xml, листов и таблиц запросов, риск испортить книгу больше пользы.
- Идеи: перенос фильтров выше точки разрыва свёртки (нужен анализ используемых столбцов);
  разбор `Value.NativeQuery` для свёртки; типы столбцов по шагам (вывод схемы) — для автодополнения.
